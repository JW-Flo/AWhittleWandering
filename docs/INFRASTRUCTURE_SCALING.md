# Infrastructure Scaling Guide

This guide explains how to scale the AWhittleWandering infrastructure for customer onboarding and multi-environment deployments.

## Overview

The AWhittleWandering platform uses Cloudflare Workers with D1 databases and KV namespaces. To support smooth customer onboarding and multi-environment deployments, we provide automated provisioning scripts and clear processes.

## Quick Start: Provision a New Environment

### 1. Run the Provisioning Script

```bash
# Provision staging environment
bash scripts/provision-environment.sh staging

# Provision customer environment
bash scripts/provision-environment.sh customer-acme
```

The script will:
1. ✅ Create a new D1 database
2. ✅ Create a new KV namespace
3. ✅ Generate wrangler.toml configuration
4. ✅ Provide secrets setup checklist
5. ✅ Save resource IDs to `.env.<environment>.resources`

### 2. Update `wrangler.toml`

Copy the generated configuration from the script output and add it to `backend/edge-worker/wrangler.toml`.

Example output:
```toml
[env.staging]
name = "awhittlewandering-api-staging"

[env.staging.vars]
AI_GATEWAY_ID = "awhittlewandering-ai"
AI_MODEL_NAME = "@cf/meta/llama-3.1-8b-instruct"
LOG_LEVEL = "info"
ENVIRONMENT = "staging"

[[env.staging.d1_databases]]
binding = "TESLA_DB"
database_name = "tesla-journey-tracker-staging"
database_id = "abc123..."  # Generated by script

[[env.staging.kv_namespaces]]
binding = "AUTH_TOKENS"
id = "def456..."  # Generated by script

[[env.staging.analytics_engine_datasets]]
binding = "TELEMETRY_ANALYTICS"

[env.staging.ai]
binding = "AI"
```

### 3. Set Environment Secrets

```bash
wrangler secret put TESSIE_API_TOKEN --env staging
wrangler secret put MAPBOX_API_TOKEN --env staging
wrangler secret put OPENWEATHER_API_KEY --env staging
wrangler secret put JWT_SECRET --env staging
wrangler secret put TESLA_VIN --env staging
```

### 4. Apply Database Migrations

```bash
cd backend/edge-worker
wrangler d1 migrations apply TESLA_DB --env staging --remote
```

### 5. Deploy to the New Environment

```bash
cd backend/edge-worker
wrangler deploy --env staging
```

### 6. Verify Deployment

```bash
# Health check
curl https://api-staging.awhittlewandering.com/api/v1/health

# Or if using workers.dev subdomain:
curl https://awhittlewandering-api-staging.{account-id}.workers.dev/api/v1/health
```

## Customer Onboarding Process

### For New Customer Environments

When onboarding a new customer that needs an isolated environment:

1. **Provision Resources**
   ```bash
   bash scripts/provision-environment.sh customer-acme
   ```

2. **Update Configuration**
   - Add the generated `[env.customer-acme]` block to `wrangler.toml`
   - Commit the configuration to git

3. **Set Customer Secrets**
   ```bash
   wrangler secret put TESSIE_API_TOKEN --env customer-acme
   wrangler secret put TESLA_VIN --env customer-acme
   # ... other required secrets
   ```

4. **Deploy Customer Environment**
   ```bash
   wrangler deploy --env customer-acme
   ```

5. **Configure Custom Domain (Optional)**
   Add to `wrangler.toml`:
   ```toml
   [[env.customer-acme.routes]]
   pattern = "api-acme.awhittlewandering.com/*"
   zone_name = "awhittlewandering.com"
   ```

### Scaling Considerations

#### Database Scaling
- **D1 Limits**: Each D1 database supports millions of rows
- **Isolation**: Each customer gets their own database instance
- **Backups**: Use D1 Time Travel (30-day window) for point-in-time recovery
- **Migrations**: Forward-only, tested in staging before production

#### KV Scaling
- **Limits**: Each KV namespace supports billions of key-value pairs
- **Isolation**: Each customer gets their own KV namespace
- **TTL**: Use automatic expiration for session tokens
- **Consistency**: Eventually consistent (60 seconds global propagation)

#### Worker Scaling
- **Limits**: Cloudflare Workers auto-scale to millions of requests
- **Cold Starts**: Workers have near-zero cold start time
- **Concurrency**: Each worker handles concurrent requests efficiently
- **Cost**: Pay-as-you-go based on requests and CPU time

## Environment Management

### List All Provisioned Environments

```bash
# List all D1 databases
wrangler d1 list

# List all KV namespaces
wrangler kv:namespace list
```

### View Environment Configuration

```bash
# View resource IDs for an environment
cat .env.staging.resources
```

### Delete an Environment

**⚠️ WARNING: This is destructive and cannot be undone!**

```bash
# Delete D1 database
wrangler d1 delete tesla-journey-tracker-staging

# Delete KV namespace
wrangler kv:namespace delete --namespace-id "abc123..."

# Remove from wrangler.toml
# (Edit file to remove [env.staging] block)
```

## Multi-Environment Deployment Pipeline

### Using GitHub Actions

The repository includes deployment workflows that support multiple environments:

```yaml
# .github/workflows/deploy-staging.yml
name: Deploy Staging
on:
  push:
    branches: [main]
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Deploy to Staging
        run: wrangler deploy --env staging
```

### Using Gastown/Beads Formulas

The repository includes Beads formulas for multi-environment deployments:

```bash
# Deploy to staging
bd run deploy-staging

# Deploy to production
bd run deploy-production
```

## Troubleshooting

### Provisioning Failures

**Error: "Not authenticated with Cloudflare"**
```bash
wrangler login
```

**Error: "Database already exists"**
- The script will detect existing resources and reuse them
- Check `.env.{environment}.resources` for existing IDs

### Deployment Failures

**Error: "Database binding not found"**
- Verify the database ID in `wrangler.toml` matches the provisioned resource
- Run `wrangler d1 list` to confirm the database exists

**Error: "KV namespace not found"**
- Verify the KV namespace ID in `wrangler.toml` matches the provisioned resource
- Run `wrangler kv:namespace list` to confirm the namespace exists

### Migration Failures

**Error: "Migration failed"**
- Check migration SQL syntax
- Verify the environment name matches exactly
- Use D1 Time Travel to rollback if needed:
  ```bash
  wrangler d1 time-travel restore TESLA_DB --env staging --timestamp 2026-02-06T15:00:00Z
  ```

## Best Practices

### Security

1. ✅ **Never commit secrets** to `wrangler.toml` or `.env` files
2. ✅ **Use `wrangler secret put`** for all sensitive values
3. ✅ **Isolate customer data** with separate environments
4. ✅ **Rotate secrets regularly** (JWT_SECRET, API tokens)

### Testing

1. ✅ **Test in staging first** before deploying to production
2. ✅ **Run migrations in staging** to validate SQL
3. ✅ **Verify health checks** after each deployment
4. ✅ **Monitor error rates** in Cloudflare analytics

### Deployment

1. ✅ **Use CI/CD pipelines** for automated deployments
2. ✅ **Enable auto-rollback** in case of failures
3. ✅ **Tag releases** with semantic versioning
4. ✅ **Backup before migrations** using D1 export

### Cost Optimization

1. ✅ **Use KV TTL** for temporary data (sessions, cache)
2. ✅ **Optimize SQL queries** to reduce D1 read units
3. ✅ **Cache frequently accessed data** in KV
4. ✅ **Monitor usage** in Cloudflare dashboard

## Resource Limits

### D1 Database (per database)

- **Storage**: 10 GB (free), 50+ GB (paid)
- **Reads**: 25M reads/month (free), unlimited (paid)
- **Writes**: 100K writes/month (free), unlimited (paid)
- **Row Size**: 1 MB max
- **Table Size**: Unlimited rows (subject to storage limit)

### KV Namespace (per namespace)

- **Storage**: Unlimited
- **Keys**: Unlimited
- **Value Size**: 25 MB max
- **Reads**: 100K reads/day (free), unlimited (paid)
- **Writes**: 1,000 writes/day (free), unlimited (paid)
- **Propagation**: 60 seconds globally

### Workers (per account)

- **Requests**: 100K requests/day (free), unlimited (paid)
- **CPU Time**: 10ms per request (free), 50ms (paid)
- **Memory**: 128 MB per request
- **Scripts**: 100 scripts (free), unlimited (paid)
